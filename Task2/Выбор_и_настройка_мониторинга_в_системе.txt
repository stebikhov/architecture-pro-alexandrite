Сокращения:
Термин        | Расшифровка
--------------|--------------------------------------------------------------

MTTD          | Mean Time To Detection — среднее время обнаружения инцидента

Мотивация

В компании «Александрит» до сих пор нет системного мониторинга бэкенда. Яндекс
Метрика показывает только клиентскую активность и не отражает состояние
очередей, БД и межсервисных взаимодействий.

После открытия API для партнёров нагрузка на систему выросла, из-за чего
повысился риск сбоев и потери крупных контрактов. Выявлены проблемы, диагностика
 которых невозможна без телеметрии:
- задержки в обработке заказов;
- потери сообщений в RabbitMQ;
- увеличение времени отклика MES API на запросы дашборда первой страницы;
- отсутствие сквозного контроля статусов заказа.

Инциденты выявляют только по жалобам клиентов и операторов — из-за этого
диагностика сильно затягивается.

Цели мониторинга:

- Раннее обнаружение инцидентов. Алерты позволяют реагировать на аномалии до
жалоб клиентов.
- Быстрая локализация проблем. Метрики сразу показывают, какой компонент
деградирует. Например, жалобы операторов на долгую загрузку дашборда MES мы
сможем подтверждать или опровергать за минуты, а не часы — это напрямую
сокращает среднее время устранения инцидента (MTTR).
- Обоснованное масштабирование. Нагрузка растёт линейно: примерно на 100 заказов
 в месяц. Метрики дают реальные данные для обоснованных решений о масштабировании.
- Контроль бизнес-процессов. Клиенты регулярно жалуются на срывы сроков: изделие
 должно быть готово за три недели, но фактически работа затягивается на месяцы.
Мониторинг статусов заказов выявляет узкие места в цепочке CRM → RabbitMQ → MES.

Это снизит потери заказов, уменьшит нагрузку на поддержку и сохранит репутацию
надёжного поставщика.

Выбор подхода к мониторингу

В системе «Александрит» присутствуют разнородные компоненты: веб-приложения с
внешними пользователями (Internet Shop, CRM, MES), асинхронная очередь сообщений
 (RabbitMQ), БД (PostgreSQL) и внешнее API для партнёров (MES API).
Компоненты разнородны — веб-сервисы, очередь сообщений, БД. Поэтому для
них нужны разные подходы к мониторингу.

Компоненты, покрываемые мониторингом, отмечены на C4-диаграмме
.data/jewerly_c4_model.drawio (страница «Monitoring») зелёным цветом. На схеме
выделены:
- Shop API, CRM API, MES API — для сбора RED-метрик;
- RabbitMQ — для сбора USE-метрик очереди;
- Shop Database, MES Database — для сбора USE-метрик СУБД;
- Точки межсервисного взаимодействия (Shop API → RabbitMQ, RabbitMQ → CRM API,
MES API → RabbitMQ) — для сквозного контроля бизнес-процесса.

В C4-диаграмме jewerly_c4_model.drawio идентифицированы три точки межсервисного
взаимодействия, критичные для мониторинга:
1. Публикация сообщений из MES в RabbitMQ — асинхронная передача событий о
расчёте стоимости и изменении статусов заказов.
2. Потребление сообщений CRM API из очереди — приём событий от MES и обновление
статусов в CRM.
3. Синхронный вызов MES API со стороны внешних партнёров через Shop API —
HTTP-запросы к сервису расчёта стоимости.

Мониторинг каждой из этих связей ведётся отдельно: деградация на любом участке
нарушает сквозной поток обработки заказа. Контролируя границы взаимодействия,
можно точно локализовать проблему: понять, где возникла задержка — при
публикации сообщений, обработке в очереди или в синхронном вызове.

Для API-сервисов (Shop API, CRM API, MES API) применяем подход RED:
- Rate — число HTTP-запросов в секунду. Показывает нагрузку и всплески трафика.
- Errors — доля ошибок 5xx. Индикатор сбоев и таймаутов.
- Duration — время обработки запросов (p50, p90, p99). Отражает скорость работы
и пользовательский опыт.

RED позволяет быстро замечать деградацию: рост ошибок и увеличение времени
ответа пользователи замечают сразу.

Для RabbitMQ и PostgreSQL (Shop Database, MES Database) используем подход USE
(Utilization, Saturation, Errors): отслеживаем утилизацию ресурсов (процессор,
память, диск, сеть), насыщение очередей и соединений, а также частоту ошибок.

Для сквозного контроля бизнес-процесса (прохождение заказа по статусам)
используем четыре золотых сигнала: задержка, трафик, ошибки и насыщение. Они
дают бизнес-метрики, которые нельзя получить из показателей отдельных сервисов.

Таким образом, в системе используется комбинированный подход:

Компонент (C4-диаграмма)        | Подход                | Обоснование
--------------------------------|-----------------------|----------------------------------------------
Shop API (Spring Boot)          | RED                   | HTTP-сервис с внешними пользователями
CRM API (Spring Boot)           | RED                   | HTTP-сервис с внешними пользователями
MES API (C#)                    | RED                   | HTTP-сервис, обслуживающий внешних пользователей и API-клиентов
RabbitMQ                        | USE                   | Инфраструктурный компонент: очередь сообщений
Shop Database (PostgreSQL)      | USE                   | Инфраструктурный компонент: СУБД
MES Database (PostgreSQL)       | USE                   | Инфраструктурный компонент: СУБД
Поток заказов (сквозной)        | Четыре золотых сигнала| Бизнес-процесс, пересекающий несколько сервисов

Метрики

Метрики отобраны по следующим критериям:
- связь с зафиксированными инцидентами (жалобы клиентов, операторов, потеря
контрактов);
- возможность количественной оценки через доступные источники данных (логи,
телеметрия, таблицы статусов);
- чувствительность к деградации производительности (перцентили p90, p99, queue
depth, DLQ).

Основанием для выбора служат пункты описания кейса: рост нагрузки (100
заказов/месяц), жалобы на просроченные заказы, задержки загрузки дашбордов,
потери заказов.

Метрики, не включённые в первую очередь

Следующие метрики не включены в приоритетный набор, так как не помогают напрямую
 выявлять ключевые инциденты — задержки обработки заказов, потери сообщений и
жалобы операторов. Их добавление планируется на втором этапе для оценки
масштабируемости.

Метрика                    | Причина исключения из первой очереди                             | Планируемый срок добавления
---------------------------|------------------------------------------------------------------|----------------------------------
HTTP Request Rate          | Не помогает выявлять конкретные инциденты                        | После внедрения базового мониторинга (30 дней)
CPU Utilization            | Инфраструктурная метрика, не отражающая бизнес-процессы          | После внедрения базового мониторинга (30 дней)
Active Database Connections| Позволяет выявлять утечки соединений, но не является приоритетной| После внедрения базового мониторинга (30 дней)
Memory Utilization         | Общая метрика инфраструктуры, не связана напрямую с проблемами   | На усмотрение команды после стабилизации
Disk I/O                   | Инфраструктурная метрика, не критична для текущих инцидентов     | На усмотрение команды после стабилизации
Network Throughput         | Не помогает локализовать проблемы обработки заказов              | На усмотрение команды после стабилизации

HTTP Request Rate — количество входящих HTTP-запросов в секунду по всем
API-сервисам. Позволяет отслеживать нагрузку и выявлять аномальные всплески
трафика.

CPU Utilization — процент использования процессора экземплярами БД и
очереди сообщений. Стабильное превышение 80 % свидетельствует о необходимости
оптимизации либо масштабирования.

Active Database Connections — количество активных соединений с БД.
Позволяет выявлять утечки соединений либо исчерпание пула соединений.

Механизм расчёта сквозных метрик

Уникальный идентификатор заказа (order_id) генерируется в Shop API при создании
заказа (статус INITIATED) и сохраняется в таблице orders. В дальнейшем order_id
передаётся во всех сообщениях RabbitMQ (в поле correlation_id заголовка
сообщения) и фиксируется в таблицах статусов CRM и MES. Для обеспечения
целостности данных реализованы следующие механизмы:
- неизменяемость order_id после генерации;
- валидация наличия order_id на входе всех сервисов (Shop API, CRM API, MES
API);
- логирование ошибок при отсутствии или несоответствии order_id.

order_id служит ключом корреляции: по нему сервис-агрегатор объединяет статусы
заказа из CRM, MES и RabbitMQ для расчёта сквозных метрик — Stuck Orders Count и
 End-to-End Latency.

Расчёт метрики Stuck Orders Count основан на данных о статусах заказов,
передаваемых из CRM и MES через RabbitMQ. Агрегацию выполняет отдельный
сервис-агрегатор: он ежесекундно собирает данные о статусах и рассчитывает
длительность нахождения заказа в каждом из них. Пороговое значение определяется
на основании бизнес-правил для статусов заказа.

Расчёт метрики Order End-to-End Latency выполняется путём вычисления разности
между временными метками перехода заказа в статус INITIATED и CLOSED. Временные
метки извлекаются из таблиц статусов CRM и MES, синхронизированных через
RabbitMQ. Агрегация производится сервисом-агрегатором с группировкой по
источнику заказа (online shop, API-партнёры) и типу продукта.

Учитываем граничные случаи, чтобы не искажать метрики:
- заказы в статусе CANCELLED не участвуют в расчёте End-to-End Latency;
- если заказ не переходит из SUBMITTED в PRICE_CALCULATED за 60 минут — считаем
его зависшим (Stuck Orders Count);
- заказы без валидного order_id фиксируем в метрике Invalid Orders Count для
дальнейшего анализа.

Эти правила позволяют корректно агрегировать данные и избежать искажения
бизнес-метрик.

План действий

Этап                           | Цель                                      | Основные результаты                                                           | Ответственные
-------------------------------|-------------------------------------------|-------------------------------------------------------------------------------|---------------------------
1. Инфраструктура мониторинга  | Обеспечить сбор, хранение и визуализацию  | Развёрнуты Prometheus, Grafana, Alertmanager; настроен service discovery      | DevOps
2. Инструментирование сервисов | Обеспечить экспорт телеметрии             | Сервисы Shop API, CRM API, MES API экспортируют метрики; настроены экспортеры | Бэкенд-разработчики, DevOps
3. Визуализация                | Сформировать набор дашбордов              | Дашборды: «Общее состояние системы», «API-сервисы», «Очередь и БД»            | DevOps, аналитики
4. Алертинг                    | Настроить систему оповещений              | Определены пороги и уровни критичности; настроены каналы уведомлений          | DevOps, техлиды

Низкоуровневые шаги (например, «настроить автоматическое обнаружение сервисов»)
вынесены в приложение или отдельный чеклист.

Показатели насыщенности и пороги срабатывания

Показатели насыщенности задают пороговые значения, при превышении которых
система не справляется с нагрузкой и требуется вмешательство оператора.

Компонент             | Метрика                           | Порог                                          | Обоснование                                                  | Действия
----------------------|-----------------------------------|------------------------------------------------|--------------------------------------------------------------|------------------------------------------------------------------
MES API               | HTTP Request Duration (p99)       | >10 сек на эндпоинте дашборда в течение 15 мин | Операторы не успевают реагировать на новые заказы            | High-тикет, уведомление в Telegram; эскалация тимлиду при сохранении >30 мин
RabbitMQ              | Queue Depth (Warning)             | >1000 сообщений в течение 10 мин               | Допустимая задержка обновления статусов — не более 100 мин   | Medium-тикет, уведомление в рабочий канал
RabbitMQ              | Queue Depth (Critical)            | >5000 сообщений в течение 20 мин               | Задержка свыше 8 часов нарушает обязательства перед клиентами| Critical-тикет, проверка производительности потребителей, масштабирование
PostgreSQL (MES DB)   | Active Database Connections       | >90% от лимита в течение 10 мин                | Исчерпание пула соединений приводит к ошибкам подключения    | Critical-тикет, запрос в поддержку Yandex Cloud на увеличение лимита
Сквозной поток        | Stuck Orders Count                | >100 заказов в SUBMITTED без перехода 60 мин   | Зависшие заказы означают сбой в цепочке                      | Highest-тикет, оповещение команды через Telegram и email; голосовая нотификация

Пороги предварительные: формального SLA пока нет. В первые 30 дней эксплуатации
их уточнят на основе реальных данных. Действия при срабатывании алертов
регламентированы отдельным документом.
