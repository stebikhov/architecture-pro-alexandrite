Данные, которые должны попадать в трассировку

Для обеспечения сквозной видимости необходимо фиксировать следующие данные:

Спаны типов HTTP, СУБД и messaging создаются по семантическим соглашениям
OpenTelemetry (версия 1.26), с домен-специфичными атрибутами:
- order.id — бизнес-идентификатор заказа, используемый для агрегации трасс по
клиентскому запросу;
- order.status — статус заказа на момент выполнения операции, соответствующий
модели статусов, описанной в разделе «Статусы заказа» технического задания;
- messaging.rabbitmq.routing_key — ключ маршрутизации сообщения в RabbitMQ,
позволяющий идентифицировать тип события (создание заказа, смена статуса);
- messaging.message.id — уникальный идентификатор сообщения в очереди,
используемый для корреляции при подозрении на потерю;
- messaging.destination.name — имя очереди или топика RabbitMQ.

Переход между статусами фиксируется как событие в спане (OpenTelemetry
AddEvent), например: span.AddEvent("order.status_changed", attributes).

Мотивация

Почему в систему нужно добавить трассировку

Сейчас при сбое мы вынуждены вручную сопоставлять логи по всем компонентам — это
 долго и ненадёжно. Трассировка закрывает эти проблемы:

- Сквозная видимость: каждый заказ получает идентификатор трассы, который
передаётся между сервисами. В Jaeger весь путь заказа виден в одной цепочке
спанов — от создания до завершения производства.
- Быстрая диагностика: при жалобе клиента достаточно ввести order.id в Jaeger UI
 — сразу видно, на каком этапе задержка и где ошибка. Это полностью заменяет
ручное сопоставление логов.
- Выявление узких мест: анализ распределения времени между спанами показывает,
какой сервис или операция вносит наибольший вклад в общую задержку выполнения
заказа.
- Корреляция событий: трассировка позволяет связать события в разных сервисах,
которые относятся к одному заказу, без необходимости ручного сопоставления по
времени и идентификаторам.

Метрики решения

Мы оцениваем эффективность по метрикам, которые напрямую закрывают наши боли:
MTTD и MTTR — чтобы быстрее находить и чинить инциденты; процент потерянных
заказов — чтобы контролировать надёжность цепочки.

Технические метрики:

- MTTD (Mean Time To Detection) — время от появления проблемы до её обнаружения.
 Сейчас инциденты всплывают только по жалобам — и это обычно через несколько
часов. Трассировка с алертами позволит фиксировать проблемы в течение минут, ещё
 до обращения клиента.

- MTTR (Mean Time To Resolution) — среднее время устранения инцидента. MTTR
сократится на 40–60% за счёт того, что в Jaeger мы сразу увидим проблемный этап
— не придётся вручную сопоставлять логи по всем сервисам.

- Процент заказов с полной сквозной трассировкой. Для заказов с ошибками и
аномально долгим временем обработки сохраняем полную трассировку (цель — охват
99%). Для остальных используем выборку 10%: этого достаточно для оценки
распределения задержек.

Бизнес-метрики:

- Процент потерянных заказов — доля заказов, не выполненных по техническим
причинам. При внедрении мониторинга потерянных трасс (см. раздел «Автоматический
 мониторинг») прогнозируется снижение до значений, определяемых надёжностью
RabbitMQ и механизмов dead-letter обработки.

- Среднее время выполнения заказа (Order End-to-End Latency) — время от создания
 заказа клиентом до получения. Цель — сократить среднее время выполнения заказа,
 потому что сейчас задержки приводят к жалобам клиентов и потере репутации.

- Количество жалоб клиентов на потерю заказов — абсолютное число обращений в
поддержку по поводу незавершённых заказов. Целевое значение: снижение на 80% в
течение 3 месяцев после внедрения трассировки.

- Процент заказов, выполненных в срок — доля заказов, завершённых в рамках
нормативного времени (3 недели для стандартных изделий). Целевое значение: ≥95%
в течение 6 месяцев.

- Удовлетворённость клиентов (CSAT) — оценка качества обслуживания по опросам
клиентов. Целевое значение: рост с 3,2 до 4,5 баллов (по 5-балльной шкале) в
течение 6 месяцев.

- Количество повторных заказов — метрика лояльности клиентов. Целевое значение:
рост на 25% в течение 6 месяцев после устранения проблем с потерей заказов.

Технологии

Для реализации распределённой трассировки выбран следующий технологический стек:

1. OpenTelemetry — стандарт де-факто для инструментирования приложений.
Предоставляет единый API для генерации трасс, поддерживает автоматическую
передачу контекста между сервисами, имеет библиотеки для Java (Spring Boot) и
.NET (C#).

2. Jaeger — система хранения и визуализации трасс с открытым исходным кодом.
Jaeger выбрали, потому что для нас критично быстро искать трассы по order.id, а
у Jaeger удобнее поиск и фильтрация по тегам. Плюс в команде уже есть опыт с ним
 — это снижает риски внедрения.

3. OpenTelemetry Collector — компонент для приёма, обработки и экспорта трасс.
Позволяет буферизовать данные, применять фильтрацию и маршрутизацию, снижает
нагрузку на Jaeger. Используем tail-based sampling: решение о сохранении трассы
принимаем после завершения запроса. Так мы гарантированно не потерям трассы с
ошибками — в отличие от head-based подхода.

Архитектура решения

Как показано на странице «1. Tracing», в архитектуру добавлены OpenTelemetry
Collector и Jaeger (выделены красным). Трассировка реализуется по следующей
схеме:

1. Онлайн-магазин API (Spring Boot) — при создании заказа генерируется новая
трасса с идентификатором заказа. Библиотека opentelemetry-javaagent
автоматически инструментизирует HTTP-запросы, вызовы JDBC и отправку сообщений в
 RabbitMQ. Контекст трассы передаётся в соответствии со спецификацией W3C Trace
Context: для HTTP-запросов используется заголовок traceparent, для сообщений
RabbitMQ — свойство headers.traceparent, поддерживаемое библиотекой
opentelemetry-instrumentation-amqp.

2. CRM API (Spring Boot) — при потреблении сообщения из RabbitMQ контекст трассы
 извлекается из заголовков сообщения. Все последующие операции (запись в БД,
отправка сообщений) выполняются в рамках той же трассы.

3. MES API (C#) — при потреблении сообщения из RabbitMQ контекст трассы
извлекается из заголовков. Для инструментирования используется библиотека
OpenTelemetry.Instrumentation.AspNetCore и OpenTelemetry.Exporter.Jaeger.
Контекст передаётся через заголовки сообщений.

4. OpenTelemetry Collector — развёртывается как отдельный контейнер или pod в
Kubernetes. Принимает трассы от всех сервисов по протоколу OTLP, буферизует и
экспортирует в Jaeger. Для снижения объёма хранимых данных при сохранении
диагностической ценности применяется tail-based sampling на уровне OpenTelemetry
 Collector: трассы с ошибкой или длительностью выше 95-го процентиля сохраняются
 полностью, остальные — с вероятностью 10%.

5. Jaeger — развёртывается в режиме all-in-one для тестовой среды с хранением в
оперативной памяти. Для production-среды хранение организуется в кластере
Elasticsearch, что обеспечивает устойчивость данных при перезапуске компонентов
и возможность построения долгосрочной аналитики.

Автоматический мониторинг прохождения заказа и алертинг (дополнительное задание)

На базе трасс строится система мониторинга и алертинга, которая:

1. Мониторинг времени прохождения заказа. Скрипт регулярно опрашивает Jaeger по
order.id и считает длительность этапов. При превышении порога он автоматически
создаёт алерт и отправляет уведомление в Telegram-канал команды. Пороги
установлены на основании нормативного времени: PRICE_CALCULATED — 35 минут,
MANUFACTURING_STARTED — 24 часа, MANUFACTURING_COMPLETED — 72 часа, SHIPPED —
168 часов. Заказы в статусе INITIATED, не перешедшие в SUBMITTED за 24 часа,
исключаются из алертинга как незавершённые сессии.

2. Мониторинг потерянных трасс. Скрипт сравнивает количество заказов, созданных
в онлайн-магазине, с количеством трасс, достигших MES. Расхождение указывает на
потерю сообщений в RabbitMQ.

3. Алертинг. При превышении порогов система создаёт тикет в задачном трекере и
отправляет оповещение в Telegram-канал команды.

Компоненты мониторинга и алертинга выделены зелёным цветом на второй странице
(«2. Tracing + Alerting») файла Task3/jewerly_c4_model_tracing.drawio:
- Order Monitoring Service;
- Alert Manager;
- Task Tracker;
- Telegram Channel;
- связь «Jaeger → Order Monitoring Service»;
- связь «Order Monitoring Service → Alert Manager»;
- связь «Alert Manager → Task Tracker» (создание тикета);
- связь «Alert Manager → Telegram Channel» (отправка оповещения).

Компромиссы

Ограничения трассировки

1. Потеря контекста между сервисами. Если один из сервисов не передаёт контекст
трассы (например, проприетарная MES не поддерживает заголовки трассировки),
сквозная трасса будет разорвана. В этом случае трассировка покажет только часть
пути заказа. Для полной видимости требуется доработка всех сервисов, что может
быть дорого для проприетарных систем. Чтобы быстрее получить ценность и не
перегружать инфраструктуру, планируем поэтапное внедрение: сначала трассируем
критический путь (создание заказа → расчёт стоимости), а затем расширяем
покрытие на остальные этапы. Такой подход уже показал свою эффективность в
похожих проектах.

2. Шум данных. При полном инструментировании всех операций объём трасс может
затруднить анализ. Необходимо настраивать sampling и фильтровать малозначимые
операции.

3. Невозможность трассировки внешних зависимостей. Трассировка не покроет
внешние системы (транспортные компании, платёжные шлюзы), которые не
интегрированы в систему трассировки. Для таких случаев потребуется корреляция по
 логам.

Случаи высокой стоимости реализации

1. Инструментирование проприетарной MES. MES куплена вместе с исходным кодом, но
 доработка системы трассировки может потребовать значительных усилий
из-за сложности внутренней архитектуры. Если стоимость доработки превысит
пользу, целесообразно ограничиться трассировкой только на границах MES (вход и
выход сообщений).

2. Трассировка фронтенда. Инструментирование Vue- и React-приложений для
трассировки на стороне клиента требует дополнительных библиотек и может повлиять
 на производительность фронтенда. На первом этапе трассировка реализуется только
 на бэкенде.

3. Высокая стоимость хранения. При среднесуточном объёме 5000 заказов и 15
спанах на заказ объём хранимых данных с учётом tail-based sampling составляет
порядка 20–35 МБ в сутки, что при политике хранения 30 суток требует не более 1
ГБ дискового пространства в кластере Elasticsearch. Необходимо применять
выборочную запись (sampling) и политику удаления старых данных.

Безопасность

Меры предотвращения несанкционированного доступа

Система трассировки изолирована: Jaeger UI и API Collector недоступны извне.
Пользователи API и клиенты онлайн-магазина не получают прямого доступа к
трассам; информация о статусе заказа предоставляется через существующие
интерфейсы CRM и онлайн-магазина.

1. Аутентификация в Jaeger UI. Доступ к Jaeger UI защищается обратной
прокси-аутентификацией через корпоративный шлюз. Войти в систему смогут только
сотрудники компании с актуальной учётной записью.

2. Ролевая модель. Предусмотрены две роли:
   - Поддержка — доступ к просмотру трасс, поиску по order.id, просмотру
дашбордов сервисов. Jaeger UI будет использоваться командой поддержки для
диагностики жалоб.
   - Администратор — полный доступ, включая настройку sampling, управление
хранением данных, конфигурацию алертинга.

Ролевая модель Jaeger не связана с ролевой моделью баз данных: оператор MES или
продавец, имеющие доступ к MES DB или Shop DB, не получают автоматического
доступа к Jaeger UI. Это исключает риск корреляции персональных данных клиента
через order.id при наличии доступа только к одной из систем.

3. Сетевая изоляция. Jaeger и OpenTelemetry Collector размещаются в отдельной
подсети без доступа из публичной сети. Доступ возможен только через VPN или
корпоративный шлюз.

4. Защита чувствительных данных. В состав спанов не включаются: ФИО, адрес
доставки, номер телефона, платёжные реквизиты, содержимое загруженных 3D-файлов.
 На уровне OpenTelemetry Collector чувствительные данные автоматически
маскируются: значения заменяются на REDACTED.
Так персональные данные не попадут в хранилище трасс, даже если кто-то получит
доступ к ним. Атрибут order.id является внутренним идентификатором, не
позволяющим идентифицировать клиента без доступа к базе данных. SQL-запросы
логируются без подстановки параметров.

5. Шифрование трафика. Передача трасс от сервисов к Collector и от Collector к
Jaeger осуществляется по TLS.

6. Аудит доступа. Все запросы к Jaeger UI логируются с указанием пользователя,
времени и типа операции.
