Архитектурное решение по кешированию

Мотивация

Описание проблемы и её причин

Основная причина медленной загрузки дашборда MES (Manufacturing Execution
System) — тяжёлый JOIN-запрос в методе GetOrdersList, который выполняется при
каждом запросе без использования индексов покрытия или материализованных
представлений. MES DB одновременно обслуживает чтение дашборда и запись
статусов, поэтому рост обращений к чтению снижает пропускную способность записи.
 Справочник статусов загружается из базы при каждом обращении, несмотря на
редкое изменение. С учётом роста ~100 заказов/мес нагрузка на дашборд линейно
растёт вместе с числом активных заказов, увеличивая нагрузку на MES DB.

Ожидаемый эффект от внедрения кеширования

Кеширование позволяет избежать повторного выполнения одинаковых запросов,
сокращая время отклика. По логам MES API за июнь, 95-й перцентиль отклика
эндпоинта списка заказов — 4,3 с (средняя нагрузка ~12 запросов/мин). Введение
кеширования сокращает данный показатель до величины, определяемой временем
доступа к Redis (порядка 1 мс) при попадании в кеш. Сокращение времени отклика
снижает вероятность потери вознаграждения оператором вследствие технической
задержки отображения актуального списка заказов при конкуренции за новые
позиции.

Элементы системы, включаемые в кеширование

Для кеширования выбраны следующие элементы:

1. Список заказов для дашборда операторов. Результат запроса списка заказов с
фильтрацией по статусу, сортировкой и пагинацией. Это основной источник жалоб
операторов, и именно этот элемент даёт наибольший эффект от кеширования.

2. Данные о статусах заказов. Справочная информация о доступных статусах
заказов, которая используется для отображения фильтра; согласно журналу миграций
 MES DB, состав статусов не изменялся на протяжении последних 12 месяцев.
Справочник статусов заказов рассматривается как кандидат на кеширование ввиду
низкой частоты изменения данных. Параметры инвалидации для справочника статусов
описаны в разделе «Предлагаемое решение».

3. Результаты расчёта стоимости. Кеширование результатов расчёта стоимости для
идентичных комбинаций параметров модели (число полигонов, материал)
рассматривается как мера низкого приоритета ввиду индивидуального характера
большинства 3D-моделей, на что указывает описание бизнес-процесса конструктора
изделий; статистика повторяемости параметров модели на момент подготовки
документа не собиралась. Данный сценарий не включается в объём настоящего
решения и может быть рассмотрен отдельно при появлении статистики повторяемости
запросов.

Основной приоритет — кеширование списка заказов для дашборда, так как это
непосредственно решает проблему жалоб операторов.

Предлагаемое решение

Выбор типа кеширования: серверное кеширование

Выбрано серверное кеширование в MES API на базе Redis.

От клиентского кеширования отказались: оно дублирует данные, не обеспечивает
централизованного контроля актуальности и противоречит требованиям безопасности.

1. Общие данные для всех операторов. Список заказов одинаков для всех операторов
 при заданном фильтре; клиентское кеширование привело бы к дублированию
идентичных данных в браузере каждого оператора (до 300 КБ избыточной информации
при 20 операторах).

2. Конфиденциальность. Данные о заказах содержат коммерческую информацию и не
должны храниться на клиентских устройствах. Доступ к Redis ограничен периметром
Yandex Cloud и защищён TLS и аутентификацией (Redis AUTH).

3. Частая смена статусов. Поддержание согласованности локального кеша
потребовало бы постоянного опроса сервера, нивелируя выигрыш от кеширования.

4. Централизованный контроль. Инвалидация управляется на стороне сервера единым
механизмом.

Выбор паттерна кеширования

Паттерн кеширования для списка заказов

Для реализации кеширования выбран паттерн Cache-Aside (также известный как Lazy
Loading). Паттерны Write-Through и Refresh-Ahead не годятся для этого сценария.

Write-Through здесь не сработает: при смене статуса одного заказа мы не знаем,
какие комбинации фильтров затронуты. Обновлять все возможные ключи синхронно —
значит создавать лишнюю нагрузку и риск ошибок. Refresh-Ahead тоже отпадает:
запросы операторов слишком вариативны, предсказать их невозможно.

Описание паттерна:

1. При поступлении запроса на получение списка заказов приложение сначала
обращается к кешу.
2. При попадании в кеш (cache hit) данные возвращаются из кеша.
3. При промахе (cache miss) данные запрашиваются из базы данных, записываются в
кеш и возвращаются клиенту.
4. При изменении данных (смена статуса заказа) кеш инвалидируется, и следующее
чтение загрузит актуальные данные из базы.

Почему выбран Cache-Aside, а не другие паттерны:

Ниже приведено сопоставление паттернов кеширования (Cache-Aside, Write-Through,
Refresh-Ahead) применительно к списку заказов для дашборда операторов;
сопоставление стратегий инвалидации кеша приведено отдельно, в разделе
«Сравительный анализ стратегий инвалидации».

Критерий                    | Cache-Aside                    | Write-Through                  | Refresh-Ahead
----------------------------|--------------------------------|--------------------------------|----------------------------------
Задержка операций записи    | Отсутствует                    | Присутствует                   | Отсутствует при записи
Применимость при фильтрах   | Высокая                        | Низкая                         | Низкая
Сложность реализации        | Низкая                         | Средняя                        | Высокая
Поведение при недоступности | Деградация к прямому чтению    | Требует отдельной обработки    | Требует остановки фонового процесса

Таким образом, Cache-Aside лучше всего подходит для списка заказов из-за
вариативности фильтров и отсутствия единого события обновления.

Паттерн кеширования для справочника статусов заказов

Для справочника статусов заказов применяется паттерн Cache-Aside с инвалидацией
по TTL (Time To Live, время жизни записи в кеше) продолжительностью 1 час,
поскольку перечень статусов определён на уровне бизнес-процесса и не участвует в
 конкуренции операторов за новые заказы. Паттерн Write-Through не
рассматривается ввиду отсутствия операций записи данного справочника со стороны
MES API; паттерн Refresh-Ahead избыточен для данных с редкой и предсказуемой
частотой изменения.

Диаграмма последовательности действий

Участниками диаграммы последовательности являются:
- MES Frontend — клиентское SPA-приложение на React, отображающее дашборд
операторов.
- MES API — бэкенд-сервис на C#, обрабатывающий запросы к списку заказов.
- Redis Cache — распределённое хранилище кеша.
- MES DB — база данных PostgreSQL, хранящая производственные данные о заказах.

Рисунок 1 — диаграмма последовательности операций чтения списка заказов и записи
 изменения статуса заказа (файл Task5/sequence_diagram_caching.drawio).

Диаграмма (рис. 1, файл sequence_diagram_caching.drawio) иллюстрирует три
ключевых сценария работы кеша: cache hit, cache miss и инвалидацию при смене
статуса заказа. Ключи кеша формируются по шаблону
v1:orders:list:{status}:{page}:{page_size}, где префикс v1 обеспечивает
версионирование пространства имён. При изменении контракта API или структуры
хранимых данных префикс версии увеличивается, что исключает необходимость полной
 очистки хранилища Redis при развёртывании новой версии MES API. Время жизни
записи при заполнении кеша (TTL) устанавливается равным 300 секундам в качестве
страховочного механизма.

Сценарий чтения при попадании в кеш (cache hit) включает следующие шаги: MES
Frontend направляет запрос в MES API; MES API формирует ключ по шаблону
v1:orders:list:{status}:{page}:{page_size} и обращается к Redis; при обнаружении
 записи данные возвращаются без обращения к MES DB.

Сценарий чтения при промахе кеша (cache miss) повторяет первые два шага, после
чего MES API запрашивает данные из MES DB, записывает результат в Redis с TTL 300
секунд и возвращает данные MES Frontend. Чтобы при cache miss не было всплеска
одинаковых запросов к БД, используется распределённая блокировка по ключу.

Сценарий записи изменения статуса заказа включает обновление записи в MES DB и
последующую инвалидацию в Redis ключей, соответствующих прежнему и новому
статусу заказа, а также ключа общего списка заказов.

Стратегия инвалидации кеша

Инвалидация кеша в решении — программная (по событию изменения данных) и адресная
(по конкретным ключам).

Выбрали программную инвалидацию по ключу: приложение явно удаляет затронутые
записи при изменении данных.

Описание стратегии:

При изменении данных (смена статуса заказа, создание нового заказа) приложение
явно удаляет из кеша записи, связанные с изменёнными данных. Ключ кеша формируется
 по шаблону v1:orders:list:{status}:{page}:{page_size}. При недоступности Redis
в момент инвалидации применяется политика повторных попыток с экспоненциально
возрастающим интервалом ожидания.

При смене статуса заказа инвалидируются записи кеша для:
- Старого статуса (заказ исчезнет из списка)
- Нового статуса (заказ появится в списке)
- Агрегированного запроса списка заказов без фильтрации по статусу — при
условии, что данный запрос реализован соответствующим методом эндпоинта
получения списка заказов в MES API

Почему программная инвалидация подходит:

1. Гарантированная актуальность. Кеш инвалидируется немедленно при изменении
данных, что обеспечивает операторов актуальной информацией.
2. Предсказуемость. Логика инвалидации явно выражена в коде приложения и легко
тестируется.
3. Локальность изменений. Инвалидируются только записи, связанные с изменёнными
данных, а не весь кеш.
4. Устойчивость к сбоям. Для защиты от «застревания» неактуальных данных при
пропуске команды инвалидации устанавливается страховочный TTL; при недоступности
 Redis в момент инвалидации применяется политика повторных попыток, а факт
неудачной инвалидации фиксируется в журнале приложения.

Сравительный анализ стратегий инвалидации

Приведённое ниже сопоставление относится к стратегиям инвалидации кеша списка
заказов дашборда операторов; параметры инвалидации справочника статусов
рассмотрены выше и в данное сопоставление не включены.

Рассматриваются следующие стратегии:
- Программная по ключу — приложение явно удаляет записи по конкретным ключам при
 изменении данных.
- Временная (TTL) — записи автоматически удаляются по истечении заданного
времени жизни.
- По событию БД — триггеры БД отправляют события об изменениях, которые
инициируют инвалидацию.
- Гибридная — комбинация программной инвалидации с страховочным TTL для защиты
from пропущенных событий.

Критерий            | Программная по ключу    | Временная (TTL)         | По событию БД            | Гибридная
--------------------|-------------------------|-------------------------|--------------------------|--------------------------
Актуальность данных | Мгновенная              | Задержка до истечения   | Мгновенная               | Мгновенная (с TTL)
Применимость        | Подходит                | Не подходит             | Избыточна                | Оптимальна
Сложность           | Низкая                  | Минимальная             | Высокая                  | Средняя
Надёжность          | Зависит от кода         | Автоматическая          | Зависит от инфраструктуры| Высокая
Производительность  | Минимальные расходы     | Минимальные расходы     | Нагрузка на БД           | Минимальные расходы
Гибкость            | Высокая                 | Низкая                  | Средняя                  | Высокая

Таким образом, программная инвалидация по ключу обеспечивает мгновенную
актуальность и прозрачную логику в коде, поэтому выбрана в качестве основного
механизма. Временная инвалидация (TTL) недопустима в качестве основного
механизма из-за задержки актуализации, а инвалидация по событию БД избыточна
ввиду высокой сложности и связанности. Гибридная стратегия рассматривается как
эволюционное улучшение: после стабилизации базовой программной инвалидации можно
 добавить страховочный TTL для повышения отказоустойчивости.

Сравнение вариантов решения (дополнительное задание)

Рассмотрены два варианта реализации серверного кеширования для дашборда MES.

Решение 1. Распределённое кеширование с Redis (Cache-Aside)

Описание: Внедрение Redis как распределённого кеша между MES API и MES DB. MES
API проверяет кеш перед обращением к БД. При изменении заказов кеш
инвалидируется программно.

Диаграмма: См. прилагаемую диаграмму последовательности
(sequence_diagram_caching.drawio).

Преимущества Redis в этом сценарии:
1. Существенное сокращение времени отклика при cache hit и снижение нагрузки на
MES DB.
2. Зрелые библиотеки для C# упрощают реализацию.
3. Решение масштабируется на несколько инстансов MES API.

Основные риски:
1. Redis — это отдельный компонент, который нужно обслуживать.
2. Нужно корректно обрабатывать сценарии его недоступности.
3. Возможна рассинхронизация при сбоях инвалидации.

Решение 2. Локальное кеширование в памяти процесса (in-process cache)

Описание: Использование встроенного кеширования в памяти процесса MES API
(например, IMemoryCache в ASP.NET Core) вместо распределённого кеша. Данные
хранятся в памяти каждого экземпляра приложения.

Диаграмма: Не требуется (изменения только на уровне кода MES API).

Плюсы:
1. Отсутствие дополнительного сетевого вызова при обращении к кешу, что
обеспечивает минимальную задержку.
2. Отсутствие затрат на развёртывание и обслуживание отдельного сервиса (Redis).
3. Простота реализации: не требуется интеграция с внешним хранилищем.

Минусы:
1. При горизонтальном масштабировании MES API на несколько инстансов каждый
инстанс поддерживает собственную независимую копию кеша, что приводит к
рассинхронизации данных между инстансами.
2. Инвалидация кеша требует выполнения отдельно на каждом инстансе, что
противоречит требованию о централизованном контроле актуальности данных.
3. Данные кеша теряются при перезапуске приложения.
4. Ограничение по объёму памяти: кеш делит ресурсы с основным приложением.

Сопоставление решений

Критерий                          | Решение 1: Кеширование Redis     | Решение 2: In-process cache
----------------------------------|----------------------------------|----------------------------------
Время реализации                  | 1–2 спринта                      | 1 спринт
Эффект для дашборда               | Сокращение с 4,3 с до ~1 мс      | До десятков микросекунд
Синхронизация при масштабировании | Централизованная                 | Рассинхронизация между инстансами
Сложность                         | Средняя                          | Низкая
Масштабируемость                  | Высокая                          | Ограниченная
Стоимость инфраструктуры          | Средняя (Redis-инстанс)          | Отсутствует
Риск регрессии                    | Низкий                           | Низкий, но с риском несогласованности

Таким образом, Redis предпочтительнее для сценария с горизонтальным
масштабированием и требованием централизованного контроля актуальности.

Плюсы и минусы решений описаны выше.

Заключение

Рекомендуемое решение: Решение 1 (распределённое кеширование с Redis).

Мы рекомендуем Решение 1 (Redis) by following причинам. Во-первых, компания
ожидает рост заказов и горизонтальное масштабирование MES API — Redis обеспечит
централизованный кеш для нескольких инстансов. Во-вторых, критически важна
актуальность данных: программная инвалидация по ключу даёт мгновенное обновление
списков заказов при смене статусов. Наконец, Redis можно позже использовать и
для других сценариев (например, кеширование расчёта стоимости), что снизит
стоимость будущих доработок.

Оба рассмотренных решения относятся к серверному кешированию; сопоставление
касается исключительно способа хранения кеша — распределённого или локального.

Redis имеет смысл внедрять, если планируется масштабирование MES API либо если
95-й перцентиль отклика стабильно превышает 200 мс. In-process cache может
рассматриваться как временное решение для dev-окружения или при отсутствии
планов горизонтального масштабирования.

Компромиссы

Ограничения предложенного решения

1. Дополнительная точка отказа. Redis становится критичным компонентом: при его
недоступности MES API деградирует к прямому чтению из БД, что увеличивает
нагрузку на MES DB и время отклика. Для снижения риска предусмотрено:
   - Настройка репликации Redis (Redis Sentinel или кластер).
   - Реализация fallback-логики: при недоступности Redis запросы направляются
напрямую в БД.
   - Мониторинг доступности Redis с алертами.

2. Сложность инвалидации при масштабировании. При горизонтальном масштабировании
 MES API на несколько инстансов необходимо обеспечить согласованную инвалидацию
кеша на всех узлах. Для решения используется распределённая блокировка (RedLock)
 и публикация событий инвалидации через шину событий.

3. Накладные расходы на поддержку. Redis требует отдельного инстанса,
мониторинга, резервного копирования и обновлений. Для снижения операционной
нагрузки рекомендуется использовать managed-сервис Yandex Cloud Redis.

4. Риск рассинхронизации. При сбое в механизме инвалидации кеш может содержать
устаревшие данные. Страховочный TTL (300 секунд) ограничивает окно неактуальности,
 но не исключает его полностью. Для критичных сценариев (конкуренция операторов
за заказы) допускается кратковременная неактуальность данных.

5. Ограничение по объёму памяти. Redis хранит данные в оперативной памяти, что
ограничивает максимальный размер кеша. При росте числа заказов потребуется
увеличение инстанса Redis или шардирование. Прогноз: при текущем росте ~100
заказов/месяц и среднем размере записи 1 КБ дополнительный объём составит ~100
КБ/месяц, что не требует масштабирования в ближайшие 12 месяцев.
