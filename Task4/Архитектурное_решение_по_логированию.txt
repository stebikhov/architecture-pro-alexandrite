Архитектурное решение по логированию

Анализ системы в контексте логирования

Системы, из которых требуется сбор логов

На C4-диаграмме архитектуры системы выделены ключевые компоненты, для которых
организуется централизованное логирование:

1. Онлайн-магазин API (Spring Boot) — точка входа заказов от клиентов.
Реализовано логирование событий жизненного цикла: создание заказа, загрузка
3D-файлов, валидация данных и сохранение в Shop DB.

2. CRM API (Spring Boot) — принимает сообщения из RabbitMQ и координирует
обновление статусов заказа в Shop DB. Логирование необходимо для восстановления
хронологии изменений, выявления ошибок потребления сообщений и диагностики
задержек синхронизации.

3. MES API (C#) — выполняет расчёт стоимости и управляет производственными
статусами. Логируются: время расчёта стоимости, ошибки обработки 3D-моделей,
факты назначения операторов и сбои записи в MES DB.

4. RabbitMQ — брокер сообщений. Логи позволяют выявлять потерю сообщений,
переполнение очереди, ошибки доставки и проблемы с потребителями. Для сбора
файловых логов брокера на инстансе RabbitMQ устанавливается агент Filebeat.

5. Shop DB — база данных онлайн-магазина на основе СУБД PostgreSQL. Собираются
логи медленных запросов и ошибок подключения.

6. MES DB — база данных производственного модуля на основе СУБД PostgreSQL.
Логируются медленные запросы и ошибки репликации.

Уровни логирования

Помимо уровня INFO, в системе используются следующие уровни логирования:

DEBUG — детализированная информация для отладки. Включается только в
test/dev-окружениях или временно при расследовании инцидентов в production.
Динамическое управление уровнями логирования реализовано средствами фреймворков
(Spring Boot Actuator, Serilog): детализированное логирование включается без
перезапуска сервисов.

WARN — регистрация событий, не приводящих к немедленному отказу сервиса, но
указывающих на потенциальные риски: превышение допустимого времени ответа базы
данных, повторные попытки доставки сообщений, приближение к лимитам ресурсов.

ERROR — ошибки обработки запроса, приведшие к неудачному завершению операции:
необработанное исключение в контроллере, таймаут соединения с базой данных,
ошибка записи в RabbitMQ, сбой внешнего API-вызова. Критические ошибки, делающие
 сервис неработоспособным, фиксируются с маркером critical=true.

Мотивация

Почему в систему нужно добавить логирование

В существующей архитектуре логи хранятся локально на EC2-инстансах, что
усложняет расследование инцидентов: требуется последовательный доступ к каждому
узлу, ручной поиск по временным меткам и идентификаторам заказов.

Централизованный сбор логов обеспечивает:

1. Единую точку доступа. Все логи собираются в одном хранилище, поиск
выполняется по всем сервисам одновременно.

2. Корреляцию событий. Структурированные логи с единым форматом позволяют
связывать события из разных сервисов по идентификатору заказа или трейса.

3. Сокращение времени диагностики. Поиск нужных записей выполняется за секунды
через полнотекстовый поиск.

4. Исторический анализ. Логи хранятся централизованно заданное время, что
позволяет анализировать инциденты постфактум.

5. Разгрузку поддержки. Специалисты поддержки получают доступ к поиску по логам
и могут самостоятельно отвечать на типовые вопросы клиентов.

Метрики решения

Внедрение централизованного логирования повлияет на следующие технические и
бизнес-метрики.

1. Mean Time To Diagnosis (MTTDiag). Среднее время, необходимое для локализации
причины инцидента. Текущее среднее время диагностики инцидентов составляет 2–3
часа: требуется ручной поиск по распределённым логам на нескольких
EC2-инстансах. Целевое значение MTTDiag — 5–15 минут. Оценка основана на типовых
 сценариях диагностики: формулирование поискового запроса по идентификатору
заказа или трейсу, анализ результатов и выявление корневых причин в OpenSearch.

2. Количество эскалаций в разработку. Доля обращений в поддержку, которые
требуют вмешательства разработчиков для анализа логов. Текущий уровень эскалаций
 — 40–50% обращений, что обусловлено отсутствием у специалистов поддержки
доступа к логам сервисов. Целевое снижение доли эскалаций на 40–50% достигается
за счёт предоставления специалистам поддержки самостоятельного доступа к
централизованной системе поиска по логам.

3. Время простоя дашборда оператора MES. Доля времени, когда первая страница MES
 недоступна либо загружается дольше порогового значения. Ожидаемое снижение
показателя обусловлено возможностью выявления по логам конкретных запросов,
вызывающих деградацию.

4. Root Cause Identification Rate. Доля инцидентов, причина которой установлена
исключительно на основе централизованных логов, без воспроизведения сценария или
 запроса дополнительной информации у клиента. Целевое значение — не менее 80%.

Приоритизация внедрения логирования и трейсинга

Учитывая распределение ресурсов команды и приоритеты бизнес-процессов, внедрение
 механизмов наблюдаемости осуществляется поэтапно. Приоритет отдан системам,
непосредственно участвующим в обработке потока заказов.

Приоритет| Система            | Логирование | Трейсинг | Обоснование
---------|--------------------|-------------|----------|--------------------------------------------------------------------------------
1        | Онлайн-магазин API | Да          | Да       | Точка входа заказов. Проблемы на этом этапе приводят к потере заказов до попадания в систему.
2        | RabbitMQ           | Да          | Да       | Критичный канал передачи данных между CRM и MES. Потеря сообщений — основная причина «пропавших» заказов.
3        | CRM API            | Да          | Да       | Обрабатывает сообщения из очереди и обновляет статусы. Без логирования невозможно отследить, было ли сообщение обработано.
4        | MES API            | Да          | Да       | Производственный модуль, на который жалуются операторы. Логирование расчёта стоимости и смены статусов необходимо для диагностики задержек.
5        | Shop DB            | Да          | Нет      | Логирование медленных запросов и ошибок подключения.
6        | MES DB             | Да          | Нет      | Аналогично Shop DB.

Приоритет отдан системам, непосредственно участвующим в обработке потока
заказов: их покрытие обеспечивает максимальный эффект по снижению MTTDiag и
количества эскалаций. Трейсинг вызовов к БД покрывается на уровне
инструментирования приложений; трейсинг внутренних процессов СУБД относится к
области мониторинга.

Обоснование последовательности:

1. Онлайн-магазин API (приоритет 1) — точка входа всех заказов. Проблемы на этом
 этапе приводят к потере заказов до попадания в систему, что напрямую влияет на
выручку. Логирование создания заказов и отправки в RabbitMQ позволяет быстро
выявлять сбои на старте цепочки.

2. RabbitMQ (приоритет 2) — критичный канал передачи данных между CRM и MES.
Потеря сообщений — основная причина «пропавших» заказов. Логирование публикации,
 доставки и перемещения в DLQ позволяет отслеживать жизненный цикл каждого
сообщения.

3. CRM API (приоритет 3) — обрабатывает сообщения из очереди и обновляет
статусы. Без логирования невозможно отследить, было ли сообщение обработано и
записано ли изменение статуса в Shop БД.

4. MES API (приоритет 4) — производственный модуль, на который жалуются
операторы. Логирование расчёта стоимости и смены статусов необходимо для
диагностики задержек и выявления узких мест в производстве.

5. Shop DB и MES DB (приоритеты 5-6) — логирование медленных запросов и ошибок
подключения важно для диагностики проблем производительности, но не является
критичным для отслеживания потока заказов. Трейсинг вызовов к БД покрывается на
уровне инструментирования приложений (Shop API, CRM API, MES API), поэтому
отдельное трейсинг-инструментирование СУБД не требуется.

Предлагаемое решение

Технологии логирования

В качестве технологического стека для централизованного логирования предложена
связка OpenSearch, Logstash, Filebeat и OpenSearch Dashboards:

1. OpenSearch — распределённая поисковая система с открытым исходным кодом
(лицензия Apache 2.0). Выполняет роль хранилища и движка полнотекстового поиска
по логам.

2. Logstash — конвейер обработки данных. Принимает логи от сервисов, выполняет
парсинг, обогащение и фильтрацию, отправляет в OpenSearch.

3. Filebeat — лёгкий агент для сбора логов. Устанавливается на каждый
EC2-инстанс, читает лог-файлы приложений и отправляет в Logstash или напрямую в
OpenSearch.

4. OpenSearch Dashboards — веб-интерфейс для визуализации, поиска и анализа
логов. Предоставляет возможности построения дашбордов, настройки алертов и
выполнения запросов.

Архитектура решения

Логирование реализуется по следующей схеме:

1. Каждое приложение записывает логи в локальные файлы в структурированном
формате JSON. Структура лог-записи включает поля trace_id и span_id,
зарезервированные для интеграции с механизмом распределённой трассировки.

2. Filebeat на каждом инстансе читает лог-файлы, добавляет метаданные и
отправляет пакеты в Logstash.

3. Logstash выполняет парсинг JSON, обогащает записи, применяет фильтры и
индексирует в OpenSearch.

4. OpenSearch хранит логи в индексах, организованных по типу сервиса и дате.

5. OpenSearch Dashboards предоставляет интерфейс для поиска по логам, создания
дашбордов и настройки алертов.

Схема диаграммы

Диаграмма контейнеров C4 с компонентами логирования размещена в файле:

Task4/jewerly_c4_model_logging.drawio

 синим цветом заливки; связи, отражающие поток передачи логов и спанов,
изображены пунктирной линией. Компоненты трейсинга выделены зелёным цветом.
Покрываемые мониторингом системы: Онлайн-магазин API, CRM API, MES API,
RabbitMQ, Shop DB, MES DB, 3D Files Storage.

Новые связи:

- Онлайн-магазин API → Filebeat → Logstash → OpenSearch → OpenSearch Dashboards
- CRM API → Filebeat → Logstash → OpenSearch → OpenSearch Dashboards
- MES API → Filebeat → Logstash → OpenSearch → OpenSearch Dashboards
- RabbitMQ → Filebeat → Logstash → OpenSearch → OpenSearch Dashboards
- Shop DB → Filebeat (PostgreSQL slow log) → Logstash
- MES DB → Filebeat (PostgreSQL slow log) → Logstash
- 3d files storage → Filebeat → Logstash

- OpenSearch Dashboards → Канал оповещений (Telegram / Email)

Политика безопасности

Работа с чувствительными данными

Согласно Федеральному закону № 152-ФЗ «О персональных данных», логи не должны
содержать персональные данные клиентов (ФИО, адреса, номера телефонов, email,
платёжные реквизиты). Для идентификации событий используются обезличенные
идентификаторы (order_id, customer_id), не позволяющие однозначно
идентифицировать субъекта персональных данных без доступа к основным базам
данных.

1. Исключение персональных данных из логов. В логах недопустимо присутствие
полных имён, адресов, номеров телефонов, email, платёжных реквизитов, паролей и
токенов сессий.

2. Маскирование чувствительных полей. Маскирование чувствительных полей
выполняется на уровне приложения до записи в лог. В Logstash дополнительно
настроены фильтры для замены номеров телефонов и email на маркер [REDACTED].

3. Контроль доступа к логам. Доступ к OpenSearch Dashboards защищается
корпоративной аутентификацией. Предусмотрены роли:
   - Поддержка — поиск по логам, просмотр дашбордов, без доступа к сырым логам с
 IP-адресами.
   - Разработчик — полный поиск по логам, создание дашбордов.
   - Администратор — управление индексами, настройка алертов, доступ ко всем
данным.

4. Шифрование трафика. Передача логов от Filebeat к Logstash и от Logstash к
OpenSearch осуществляется по TLS.

5. Аудит доступа. Все запросы к OpenSearch Dashboards логируются с указанием
пользователя, времени и типа операции.

Политика хранения

1. Индексы. Логи организуются в индексы по типу сервиса и дате:
logs-shop-api-2024.08, logs-crm-api-2024.08, logs-mes-api-2024.08,
logs-rabbitmq-2024.08.

2. Срок хранения. Горячее хранение: 30 дней в OpenSearch; холодное: 90 дней в
Yandex Object Storage. После 90 дней логи удаляются. Автоматизация жизненного
цикла индексов реализована средствами Index State Management OpenSearch.

3. Холодное хранение в Yandex Object Storage. Логи, выгружаемые из горячего
хранилища, архивируются в формате gzip и размещаются в бакете Yandex Object
Storage с префиксом logs-cold/{service}/{year}/{month}/. Доступ к бакету
контролируется IAM-политиками: только роли logs-reader и logs-admin имеют право
на чтение и управление архивом. Восстановление логов из холодного хранилища
выполняется вручную через OpenSearch Snapshot API при необходимости
расследования инцидентов, выходящих за рамки 30-дневного окна.

4. Размер индекса. Максимальный размер одного индекса — 50 ГБ.

5. Резервное копирование. Резервное копирование индексов выполняется средствами
инфраструктурного регламента.

6. Оценка объёма:

Режим                        | Строк в сутки  | Объём в сутки (сжатый) | Объём за 30 дней
-----------------------------|----------------|------------------------|------------------
Средний                      | 30 000–40 000  | 0,3–0,5 ГБ             | 10–15 ГБ
Пиковый (DEBUG, retry)       | до 500 000     | до 5 ГБ                | до 150 ГБ

Прогнозный объём: 20–40 ГБ в месяц на горизонте 6–12 месяцев с учётом линейного
роста нагрузки на 100 заказов в месяц.

Превращение системы сбора логов в систему анализа логов

Алертинг

На основании логов настраиваются следующие алерты:

1. Рост количества ERROR-логов. Алерт формируется при превышении количества
ERROR-логов над фоновым уровнем более чем в N раз в течение 5-минутного окна.
Указывает на систематические сбои.

2. Появление новых типов ошибок. Если в логах появляется error_type, которого не
 было в последние 24 часа — алерт. Позволяет выявлять новые типы сбоев.

3. Логирование потери сообщений. Если в логах RabbitMQ появляется запись о
перемещении сообщения в DLQ — алерт с высоким приоритетом.

4. Ошибки аутентификации. Алерт формируется при регистрации пяти и более событий
 с полем result=failure для одного значения client_ip в течение одной минуты,
что рассматривается как признак попытки атаки типа brute force.

Поиск аномалий

1. Аномалии объёма логов. Резкое увеличение количества записей о создании
заказов может указывать на DDoS-атаку или некорректную работу клиента.
OpenSearch ML позволяет детектировать такие аномалии автоматически.

2. Аномалии времени отклика. Рост среднего времени выполнения запросов,
зафиксированный в логах, детектируется через агрегации по duration_ms.

3. Аномалии паттернов. Изменение соотношения типов логов указывает на проблему в
 цепочке обработки.

Критерии выбора технологии для работы с логами

При выборе технологии для централизованного логирования руководствовались
следующими критериями:

1. Лицензия — предпочтение отдаётся решениям с полностью открытой лицензией
(Apache 2.0, AGPL v3), допускающей модификацию и распространение без
ограничений.
2. Стоимость владения — учитываются затраты на инфраструктуру, поддержку и
масштабирование. Предпочтение — self-hosted решениям с возможностью
использования managed-сервисов.
3. Масштабируемость — способность системы обрабатывать рост объёма логов без
деградации производительности. Критично горизонтальное масштабирование.
4. Функциональность поиска — полнотекстовый поиск, агрегации, поддержка ML для
обнаружения аномалий, гибкость запросов.
5. Интеграция с экосистемой — совместимость с существующими инструментами
(Filebeat, Logstash, Grafana), поддержка стандартов (OTLP, W3C Trace Context).
6. Эксплуатационная сложность — простота развёртывания, мониторинга и
обслуживания. Учитывается наличие managed-сервисов in Yandex Cloud.

Обоснование выбора OpenSearch

OpenSearch выбран из-за открытой лицензии (Apache 2.0), совместимости с
экосистемой Elastic Stack (Filebeat, Logstash) и наличия managed-сервиса в
Yandex Cloud. Функциональности OpenSearch (поиск, агрегации, ML, алертинг)
достаточно для задач наблюдаемости.

Отказ from ELK — из-за ограничений лицензии BSL; от Splunk — из-за высокой
стоимости; от Loki — из-за менее мощного полнотекстового поиска.

Технологии трейсинга

Распределённая трассировка реализуется средствами OpenTelemetry: библиотеки
инструментирования встраиваются в Shop API, CRM API и MES API и передают спаны
по протоколу OTLP в OpenTelemetry Collector, который выполняет агрегацию и
экспорт в Jaeger. Идентификаторы trace_id и span_id, зарезервированные в
структуре лог-записи (см. раздел «Архитектура решения»), совпадают с
идентификаторами трассировки, что обеспечивает переход из логов в
соответствующий трейс средствами OpenSearch Dashboards. Ввиду ограниченности
ресурсов команды на первом этапе применяется семплирование с коэффициентом 10–20
 % для высоконагруженных эндпоинтов, для событий уровня ERROR семплирование не
применяется.
